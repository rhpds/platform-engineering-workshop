= Module 10: Enable a Cloud IDE for developers
:source-highlighter: rouge
:toc: macro
:toclevels: 1

Let us take the developer experience to another level and enable developers to provision full development environments, complete with an in-browser IDE based on VS Code, podman container runtime, testing, debugging, build tools, and agentic AI. Imagine a world where developers can maintain legacy applications, add new features to growing applications, and create greenfield applications, all without having to fight with tools, dependencies, configuration, and resource constraints on their local workstations.

We will now make that happen with OpenShift Dev Spaces.

OpenShift Dev Spaces is a full featured Cloud IDE (CDE). It includes a Red Hat supported browser native instance of Code OSS (Visual Studio Code). Browser native VS Code does not make any compromises — your multi-monitor setup is safe, and your extensions are compatible.

At the heart of OpenShift Dev Spaces are containerized workspaces defined with a configuration-as-code approach.  Each workspace configuration can be tailored to a specific type of work or even a specific project.  The container images backing workspaces can be managed centrally ensuring that tools, frameworks, and languages are consistent, secure, and up-to-date. OpenShift Dev Spaces moves all of your developer workload into a container based environment running on OpenShift, with access to the cloud scale of OpenShift resources.

Empowering developers, and engineers with OpenShift Dev Spaces is like giving teams access to a whole library of virtual workstations, each of which is bespoke engineered for a particular type of work or project.

Stop battling configuration drift, conflicts, and constraints on local workstations or IDEs and embrace the power of OpenShift Dev Spaces.

You can find the documentation here: https://docs.redhat.com/en/documentation/red_hat_openshift_dev_spaces/3.30[OpenShift Dev Spaces Documentation,window=dev-spaces-docs]

== Learning objectives

By the end of this module, you will be able to:

* Create an instance of OpenShift Dev Spaces using the CheCluster custom resource
* Launch a workspace from a git repository
* Run containers in a secured, rootless environment
* Code, Build, Debug, and Test applications in a rapid feedback cycle 
* Add guardrails to Dev Spaces to set limits for CPU, Memory, and Storage use
* Create centrally managed configurations for AI harnesses
* Embed an AI harness in workspaces

== Exercise 2: Deploy an instance of OpenShift Dev Spaces

. In the **Terminal** tab, create the Argo CD Application:
+
[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -f -
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: openshift-dev-spaces
  namespace: openshift-gitops
spec:
  project: pe-workshop
  source:
    repoURL: https://gitlab-gitlab.{openshift_cluster_ingress_domain}/rhdh/ocp-pe-wkshp-dev-spaces-config.git
    targetRevision: main
    path: base
  destination:
    server: https://kubernetes.default.svc
    namespace: openshift-devspaces
  syncPolicy:
    automated:
      selfHeal: true
EOF
----

== Exercise 7: Add guardrails to developer workspaces

We have Dev Spaces installed and have successfully deployed a workspace. In this exercise we will add guardrails to our Dev Spaces configuration to set resource limits on developers, preventing them from consuming too many resources, causing disruption to other users, or wasting compute resources.

We are going to configure the following:

* **Resource Caps for Dev Spaces workspaces** — configured in the CheCluster. This setting will silently replace resource requests or limits defined in the devfile that exceed the specified caps.
* **Resource Defaults for Dev Spaces workspaces** — configured in the CheCluster. This setting will inject default values into workspaces that do not specify the values in the devfile.yaml.
* **ResourceQuotas** — an OpenShift resource that sets total limits on resource consumption in a user's Dev Spaces namespace.
* **LimitRanges** — an OpenShift resource that sets container level constraints on resource consumption.
* **Stale Workspace Pruner** — configured in a DevWorkspaceOperatorConfig resource. This setting will delete workspaces that have not been started in a configurable amount of time.

These new resources are defined in https://gitlab-gitlab.{openshift_cluster_ingress_domain}/rhdh/ocp-pe-wkshp-dev-spaces-config/-/tree/main/overlays/02-guardrails[rhdh/ocp-pe-wkshp-dev-spaces-config/overlays/02-guardrails,window=gitlab].

* `quotas.yaml` - Contains an OpenShift Template which defines ResourceQuotas and LimitRanges. The Dev Spaces operator will use the Template to create the resources in each user's Dev Spaces namespace that is managed by the operator.
* `workspace-pruner.yaml` - Defines a DevWorkspaceOperatorConfig which configures the built in workspace pruner. The time is set for 30 days.
* `patches/checluster.yaml` - Contains a patch for the CheCluster resource which will set the resource caps and defaults.

Now apply the changes to the Dev Spaces configuration:

. In the **Terminal** tab, patch the Argo CD Application:
+
[source,bash,role="execute",subs="attributes+"]
----
oc patch application openshift-dev-spaces -n openshift-gitops --type merge -p '{"spec":{"source":{"path":"overlays/02-guardrails"}}}'
----
+
Switch to the *ArgoCD* tab and note the deployed changes to the `openshift-dev-spaces` application.
+
TIP: Click the *Refresh* button if the changes have not applied yet. You should see a "devspaces-user-resource-limits" resource.
+
image::dev-spaces/guardrails-applied.png[Apply Dev Spaces Guardrails,link=self,window=blank,align="center",width=700,title=Dev Spaces: Apply Dev Spaces Guardrails]

. Switch to the *OCP Console* tab. In the left hand nav column, expand *Administration*, select *ResourceQuotas*, and from the *Project* dropdown select *pe1-devspaces*.
+
image::dev-spaces/view-resource-quotas.png[Resource Quotas,link=self,window=blank,align="center",width=700,title=Dev Spaces: Resource Quotas]

== Exercise 8: Enable an AI harness for AI enhanced development

Parasol Insurance has decided to enable the open source AI agent and coding assistant, link:https://devfile.io[Kilo Code,window=kilo_code].

We will now provision a centrally managed configuration for Kilo Code. This enables our developers to start using the harness with zero configuration. We will create a ConfigMap in the openshift-devspaces namespace which the operator will distribute to each developer's Dev Spaces namespace.

. Take a look at the ConfigMap by navigating to the https://gitlab-gitlab.{openshift_cluster_ingress_domain}/rhdh/ocp-pe-wkshp-dev-spaces-config/-/blob/main/overlays/03-ai-assistant/ai-assistant-cm.yaml[ai-assistant-cm.yaml,window=gitlab] in the GitLab repository.

[NOTE]
====
The annotations and labels on the ConfigMap are instructions for the Dev Spaces operator that tell it to mount the files defined in the ConfigMap into running workspaces at the path `/globalconfig`. There is startup logic baked into our workspace image that will inject the URL and API key into the config file and copy it into the appropriate place in the workspace. In this way, Kilo Code is automatically configured for developers to use.

This same capability can be used to distribute other global configuration, either mounted as files or injected as environment variables. It can also inject data stored in external secrets. For example, use this capability to distribute a global Maven Settings file that ensures Java dependencies are sourced from a controlled artifact registry rather than from the internet.
====

== Module summary

OpenShift Dev Spaces can deliver transformational productivity enhancements for developers and engineers.

**What the developer experienced:**

* One click to launch a workspace that is pre-engineered for work on a specific project
* Access to a full container runtime
* Preconfigured AI agents ready to assist

**What the platform team delivered invisibly:**

* **Self-Service Access to a full featured IDE** -- no Dockerfiles, no Kubernetes YAML, no pipeline definitions. The `build-deployer` and `app-deployer` Helm charts encode the platform team's standards.
* **Security by default** -- every developer gets their own isolated set of workspaces that are prebuilt with access to a curated set of tools and extensions
* **Resource Guardrails** -- ResourceQuotas, LimitRanges, and centrally managed configuration

**What this means for Parasol:**

* **Developer Productivity** -- Developers no longer have to manage the configuration of their local workstation.  Instead, they use preconfigured workspaces that were engineered by the project team using tools made available by the enterprise.
* **Increased Compliance** -- IDE extensions, Frameworks, Build tools, Dependencies, and Code all running in OpenShift not on local workstations.
* **Easier maintenance** -- Update the configuration or container images for a workspace once and all users of that workspace config get the change.

This is another example of the multiplier effect of platform engineering: engineer the workspaces once, enable everyone on the team to run it reliably.
